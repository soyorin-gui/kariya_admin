# Intranet 技术决策记录

> 更新日期：2026-10-10  
> 状态：`已确认` 表示当前开发必须遵循；变更时新增决策或标记替代关系，不直接抹去历史。

## 已确认决策

### D-001 同一 Git 主分支协作

- 状态：已确认
- 决策：家里电脑和公司个人电脑使用同一远程仓库及当前主分支开发，不为内网模块建立独立长期分支或 Worktree。
- 原因：用户明确要求轻量协作，依靠正常 Git 提交同步代码和文档。
- 约束：Codex 本地会话不是同步载体；未提交改动不会跨设备出现。Codex 不自动 commit 或 push。

### D-002 前后端使用独立 intranet 包/目录

- 状态：已确认
- 决策：后端使用 `backend/src/main/java/org/lbl/intranet/`；前端内网业务统一放在 `frontend/src/pages/intranet/`，内部再按领域拆分。
- 原因：隔离内网与个人项目业务，并支持未来整体迁移或剥离。
- 说明：前端放在 `pages/intranet` 可直接兼容当前 `src/pages/**/*.tsx` 动态扫描，避免修改路由基线。

### D-003 基线代码受保护

- 状态：已确认
- 决策：不得擅自修改既有前后端业务和公共基础设施。确需修改时，先说明原因、范围、替代方案和验证计划，并获得用户批准。
- 结果：默认在 intranet 内通过适配或组合完成需求。

### D-004 复用现有审批与实时通知

- 状态：已确认（方向）；具体适配方案待确认
- 决策：需求流转优先复用现有审批生命周期、通知服务和实时通道，不另建重复的通知/WebSocket 体系。
- 事实边界：当前 `ApprovalTaskMapper` 直接绑定部门调动表，尚不是可直接接入任意业务的通用聚合器。
- 结果：P2 前必须评审 intranet 内适配与公共审批扩展两个方案；公共扩展属于基线修改，需批准。

### D-005 不重复建设通用组件

- 状态：已确认
- 决策：优先复用现有鉴权、RBAC、统一返回、异常、主题、布局、表格、状态、文件和图表等能力。内网专属组合组件留在 intranet 内。
- 原因：保持现有技术栈和 UI 风格，控制迁移边界和维护成本。

### D-006 血缘图谱优先评估 AntV G6

- 状态：已确认
- 决策：P4 优先使用现有 `@antv/g6` 5.x 和 `G6Graph` React 封装验证血缘展示。
- 原因：依赖和生命周期封装已经存在，无需新增图库。
- 边界：是否能满足大图、布局、折叠、交互和性能要求必须通过实测；不因本决策预先扩展公共封装。

### D-007 关系型数据库优先承载血缘元数据

- 状态：已确认
- 决策：资产、字段、映射、关系、版本、证据和影响记录优先存入现有关系型数据库；G6 只负责展示。
- 原因：当前项目已有 MySQL/MyBatis-Plus 基础，关系型模型便于事务、审计和迁移。
- 边界：如 P4/P6 实测证明规模或查询无法满足，再基于数据决定是否增加图存储；当前不预设图数据库。

### D-008 Agent 复用确定性血缘分析结果

- 状态：已确认
- 决策：Agent 通过受 RBAC 控制的只读工具消费确定性遍历结果，负责检索、解释和摘要；不替代血缘事实计算和权限判断。
- 原因：影响分析需要可重复、可解释、可审计，避免模型幻觉成为业务事实。

### D-009 交易版本不可被无痕覆盖

- 状态：已确认（原则）
- 决策：需求、审批结论、交易和交易版本之间必须可追溯；变更产生新版本或明确的受控状态变化，不直接覆盖历史事实。
- 待确认：草稿版本创建时机、版本号、激活、回滚和并发变更规则。

### D-010 敏感信息不进入个人 Git 仓库

- 状态：已确认
- 决策：禁止提交真实内网数据、内部地址、账号、密钥、令牌、证书和环境配置；样例必须脱敏或虚构，真实值由目标环境注入。
- 结果：迁移文档只登记配置项名称、用途和提供方，不登记秘密值。

### D-011 内网迁移脚本独立存放，权限菜单用种子脚本写入现有 RBAC

- 状态：已确认（2026-10-10，用户确认）
- 决策：内网数据库脚本统一放在 `backend/src/main/resources/db/intranet/`，按 `V<n>__` 顺序独立管理，不修改现有 `init_schema.sql` / `init_data.sql`。内网菜单与按钮权限通过种子脚本（V2、V6）直接写入现有 `sys_menu` / `sys_role_menu`，并只给超管初始授权。
- 原因：内网模块需要可整体剥离，同时必须复用既有 RBAC 与动态菜单，而不是另建一套权限体系。
- 边界：**用户已明确此种子方式属于「复用现有 RBAC」，不按基线数据库脚本修改处理。** 但同一条边界不适用于修改 `SystemPermissionInitializer` 或基线初始化脚本——那些仍按 D-003 走批准流程。
- 已知限制：V2/V6 的 `NOT EXISTS` 守卫未排除 `sys_menu.deleted = 1`，目标库若存在同路径/同权限码的软删除菜单会静默跳过插入；执行前须核查（已登记到 `MIGRATION.md`）。
