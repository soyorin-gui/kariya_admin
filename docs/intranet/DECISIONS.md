## 已确认决策

### D-001 同一 Git 主分支协作

- 状态：已确认
- 决策：家里电脑和公司个人电脑使用同一远程仓库及当前主分支开发，不为内网模块建立独立长期分支或 Worktree。
- 原因：用户明确要求轻量协作，依靠正常 Git 提交同步代码和文档。
- 约束：Codex 本地会话不是同步载体；未提交改动不会跨设备出现。Codex 不自动 commit 或 push。

### D-002 前后端使用独立 intranet 包/目录

- 状态：已确认
- 决策：后端使用 `backend/src/main/java/org/lbl/intranet/`；前端内网业务统一放在 `frontend/src/pages/intranet/`，内部再按领域拆分。
- 原因：隔离内网与个人项目业务，并支持未来整体迁移或剥离。
- 说明：前端放在 `pages/intranet` 可直接兼容当前 `src/pages/**/*.tsx` 动态扫描，避免修改路由基线。

### D-012 可编辑字段表格抽取为 intranet 内部共享能力

- 状态：已确认（2026-10-10，用户确认）
- 状态：已更新（2026-10-11，HBase/ES 字段设计成为第二、第三个真实用例）
- 决策：仍不在基线 `frontend/src/components/` 建设业务型可编辑表格；在 `frontend/src/pages/intranet/components/` 抽取 `InlineEditableTable`、长文本编辑和省略展示，交易/HBase/ES 字段页共同复用。
- 边界：共享层只负责 Form + Table 的单行编辑骨架和长文本交互；树形结构、字段列、校验、权限、固定 `id` 保护和 API 调用仍归各业务页面。
- 原因：三个用例均属于 intranet，尚无基线业务复用；直接提升会把树形、平面表格和业务规则混入全局 API。
- 原因：AGENTS.md §3 设定的提升门槛是「多个基线业务也存在明确复用需求」，而全仓库当前只有一个行内编辑表格（按 `EditableCell` / `onCell=` / `row.editing` 等模式检索为零命中），基线复用需求为 0；AGENTS.md §4 与 D-005 也明确反对为未来假设过度封装。单一样本下固化 API 容易抽错边界。
- 抽取时的写法要求：props 驱动、不出现内网业务词汇、不 import 内网 `api`/`types`、不硬编码权限码，使将来提升只是移动文件 + 改 import。
- **已知风险**：`pages/` 下任何 `.tsx` 都会被动态页面扫描收录为菜单组件候选，没有 default 导出的组件被选中会渲染失败。2026-10-11 用户决定不修改基线扫描规则，由菜单配置操作规范避免误选；该风险不再作为抽取工作的技术阻塞。

### D-025 SmartTable 增强多条件查询配置

- 状态：已确认并实现（2026-10-11，用户明确批准基线修改）
- 决策：保留 `searchRender` 完全自定义模式，同时增强基线 `searchConfig`：字段标签、宽度、自定义控件、高级条件展开、查询/重置按钮和回车提交策略。
- 请求语义：输入值仍保存在 `search`，只有 `submit` 才复制到 `submittedSearch` 并请求；分页、排序和刷新继续使用最后一次已提交条件。
- 兼容性：已有页面均使用 `searchRender`，行为不变；只有采用 `searchConfig` 的页面启用新的标准多条件查询区。
- 原因：树形 + 行内编辑与分页存在三处硬冲突——分页会切断父子同屏（父在第一页、子在第二页则树不成立）、草稿行的假 id 排序后可能落到别的页导致翻页即"消失"、翻页会重取数据而丢失行内未提交的编辑，且"整表保存"在只能看到一页时语义不成立。基线两个树形表格（菜单管理、部门管理）同样都是 `pagination={false}`。
- 边界：行内编辑表格只有在「扁平结构 + 行级即时提交」的场景下才适合分页。antd 的 `virtual` 不是本场景的出路——虚拟滚动假定统一行高，而树形展开行与多行文本说明列都会破坏统一行高（实现上 antd 会把 `expandable` 透传给 rc-table，并非硬性禁止，需实测），本阶段不引入。

### D-015 物理删除交易时同步删除内网关联数据

- 状态：已确认（2026-10-11，用户确认）
- 决策：交易物理删除时必须同步删除对应交易字段等关联数据，不保留孤立记录。
- 当前实现：`TransactionAssetService` 在同一事务内先按 `transaction_id` 删除报文字段，再删除交易主记录；任一步骤失败则事务回滚。
- 扩展约束：后续新增交易关联表时，必须同步扩展删除逻辑和测试。
- 2026-10-11 扩展实现：`intranet_transaction_hbase_resource` 与 `intranet_transaction_es_resource` 已创建，`TransactionAssetService.remove` 已把两者纳入同一事务的删除顺序（HBase 关联 → ES 关联 → 报文字段 → 交易主记录）。
- 更正（2026-10-11 接手复核）：原记录称 `TransactionAssetServiceTest` 用 Mockito `InOrder` 断言该顺序，该测试已不在当前仓库（随 `a3b8d0b` 删除，用户确认为有意清理）。**删除顺序目前没有任何自动化断言**；用户已决定本期不补 P1 领域定向测试（D-030），该缺失作为已知风险保留。

### D-016 ES 检索回表与 HBase 直查双路径

- 状态：已确认（2026-10-11，用户确认）
- 决策：HBase 保存真实全量数据。普通条件查询先检索 ES，ES 文档的明确字段存储 HBase RowKey，再用该 RowKey 回表查询 HBase；如果交易入参已满足 RowKey 规则，则跳过 ES 直接查询 HBase。
- RowKey 元数据：RowKey 规则只作为 HBase 表的展示型元数据，P1 不建 RowKey 规则表或组件表，也不解析执行该说明。
- 建模结果：交易关联需能区分“ES 检索后回表”和“HBase 直查”两种路径；前者需标识 ES 索引、存储 RowKey 的 ES 字段和目标 HBase 表，后者只需定位 HBase 表。

### D-017 交易关联查询资源与 ES/HBase 基数约束

- 状态：已确认（2026-10-11，用户确认）
- 决策：一个交易可以关联多个查询资源，并可访问多张 HBase 表。P1 只记录交易可能访问的 ES/HBase 资源集合，不将代码中的条件分支、先后顺序、并行查询或结果合并简化成主/备路径。
- ES/HBase 基数：每个 ES 索引只对应一张 HBase 表，且只有一个 ES 字段存储该表的完整 RowKey；一张 HBase 表可被多个 ES 索引使用。
- 后续边界：若 P3 需要表达精确执行逻辑，应另行设计查询处理节点/依赖，而不是在 P1 资源关联上预设顺序。具体表名、字段、类型、长度和约束仍待用户确认。

### D-018 HBase 表锁仅作为可选展示元数据

- 状态：已确认（2026-10-11，用户确认）
- 决策：同一张 HBase 表最多配置一个固定锁标识，允许不配置或保存空值。该信息直接作为 HBase 表的展示型元数据，不建锁表或关联表。
- 运行边界：实际锁存储在 Redis，但当前应用代码不读取这个资产元数据字段。P1 不接入 Redis，不管理或展示实时锁状态。
- 数据字典：用户确认使用 `lock_key VARCHAR(255) NULL`；空输入统一保存为 `NULL`，不保留空字符串。

### D-019 HBase/ES 字段元数据范围与资产删除规则

- 状态：已确认（2026-10-11，用户确认）
- HBase 表：显式保存集市名，以“集市名 + 表名”区分如 `HDS:TABLE` 和 `PBM:TABLE` 的资产。
- HBase 字段：保留列族并默认为 `info`；保留字段名、数据类型、说明和展示顺序；数据类型可直接保存 `varchar(32)` 等完整文本，不保存中文名，不另建长度/精度字段。
- ES 字段：字段结构只有一层，不建父子树；保留字段名、数据类型、是否可搜索、是否可排序、说明和展示顺序，不保存中文名。当前数据类型范围为 `keyword`、数值类型、`date`、`text`。
- 删除规则：HBase/ES 资源使用物理删除；被交易关联时禁止删除；HBase 表被 ES 索引引用时禁止删除；ES 的 RowKey 字段禁止单独删除；解除引用后删除资源时，物理删除它自身的字段。

### D-022 交易关联数据资源按资源集合整体替换

- 状态：已确认（2026-10-11，落实 D-017 的实现决策）
- 决策：交易与 HBase 表、ES 索引的关联只保存**资源集合**，不保存顺序号、主/备标记、条件、分支或合并规则；前端一次提交，后端在单个事务内先删除该交易的全部旧关联，再按提交集合重新写入。
- 接口：`GET/PUT /api/intranet/transactions/{transactionId}/data-resources`；读取要求 `intranet:transaction:list`，写入要求 `intranet:transaction:update`。
- 校验：交易必须存在；HBase 表编号必须存在；被关联的 ES 索引必须已包含固定 RowKey 字段，否则拒绝保存；重复编号在保存前去重。
- 原因与边界：P1 只回答“这个交易可能访问哪些数据资源”，精确的查询依赖、字段映射与执行编排属于 P3，不能用顺序字段预判。

### D-024 数据资产删除保护与引用清理

- 状态：已确认（2026-10-11，落实 D-019 删除规则的实现决策）
- 决策：数据资产的物理删除必须服从引用保护，由服务层显式实现，不依赖数据库外键。
- 具体规则：HBase 表被 ES 索引或交易关联时禁止删除；ES 索引被交易关联时禁止删除；删除 HBase 表时在同一事务内先删除其字段；删除 ES 索引时先删除其字段；ES 固定 RowKey 字段禁止单独删除。
- 与 D-015 的关系：交易物理删除时，`TransactionAssetService.remove` 在同一事务内先删除该交易的全部 HBase 资源关联、ES 资源关联和报文字段，再删除交易主记录。
- 未包含：V8 未建数据库外键，绕过应用直接写库仍可制造孤立引用；P1 接受该边界，若后续引入批量导入或运维直写需重新评估。

### D-026 交易列表的 ESF/关联资源查询条件为前端样式验证用途

### D-031 新增全局「面板填满内容区」opt-in 布局约定 `page-fill` / `card-scroll`

- 状态：已确认（2026-10-11，用户批准基线修改，明确选择"抽成全站约定"方案）
- 背景：HBase/ES/交易三个字段设计页原先各自写 `.table-card { min-height: calc(100vh - 240px) }`，导致数据只有两三行时卡片仍被撑满整屏；同时全站唯一的纵向滚动容器是 `.app-content`，内容超高时整个内容区滚动、页面标题跟着滚走。
- 决策：在基线 `frontend/src/styles/global.css` 增加**主动 opt-in** 的布局约定：
  - 页面根节点加 `page-fill`：根节点占满 `.app-content`（`height: 100%`），`.page-head` 固定不伸缩，`.table-card` 默认按内容高度渲染、仅在内容超高时收缩；
  - 卡片内需要滚动的区域加 `card-scroll`：吃掉剩余高度并在内部滚动，其它同级内容（工具栏、Tabs）固定不动；
  - 表头固定：由 `InlineEditableTable` 统一给 antd Table 传 `sticky`；antd 在设了 `sticky` 后会把表头拆成独立的 `.ant-table-sticky-holder`（`position: sticky`）放在滚动区内，因此表头不随表体滚动。
- 一段必须记下来的排查结论：**给 `th` 写 `position: sticky` 在本项目里是无效的**。`scroll.x` 会让 antd 把整张表包进 `.ant-table-content`（rc-table 给它内联 `overflow-y: scroll` + `overflow-x: auto`），`th` 的 sticky 会被困在那个自身不滚动的容器里，表现就是"表头和表体一起滚"。必须用 antd 的 `sticky` 靠它拆表头。
- 明确不采用：`.app-content > *` 这类全局强制选择器。全仓库有 13 处 `.table-card`，其中 `account/security`、`account/notifications` 是多卡片/非表格布局，一刀切会改坏它们；因此必须由页面显式声明。
- 关键实现约束：`page-fill > .table-card` 必须写 `min-height: 0`。flex 项的默认最小高度是内容高度，不置 0 卡片永远不肯收缩，结果是页面继续整体滚动、滚动条落不到卡片里。
- 影响范围：新增基线 CSS 规则；`frontend/src/pages/intranet/{transaction,dataasset}/fields/index.{tsx,css}` 改为使用该约定并删除各自的 `calc(100vh - 240px)`；`frontend/src/pages/intranet/components/InlineEditableTable.tsx` 现在自带 `.card-scroll` 容器并统一设置 `sticky`。**未修改其它任何页面**。
- 顺带修复的体验问题（用户 2026-10-11 提出）：新增字段会把草稿行追加到表格末尾，原先不滚动导致"点了新增看不到反应"。现在 `InlineEditableTable` 在 `editingKey` 变化时用 `scrollIntoView({ block: 'nearest' })` 把目标行滚进视野，新增行与被编辑的屏幕外行都能正确滚动。
- 已知风险（必须浏览器实测确认）：
  1. 表头层级由 antd 自己保证（`zIndexTableSticky = zIndexTableFixed + 1`），理论上不会再被 `fixed: 'right'` 的操作列盖住；但两个字段页都用了固定列，仍需目视确认一次。
  2. 视口极矮（可用高度小于工具栏 + Tabs + 表头高度）时卡片会溢出，退化为整区滚动。
- 验证：`tsc --noEmit` 与 `npm run build` 通过；**布局效果无法由构建验证**，必须按 `HANDOFF.md` §4 的清单在浏览器实测。

### D-038 SmartTable 统一提供 `.card-scroll` 滚动容器与固定表头

- 状态：已确认（2026-10-11，用户批准修改基线，理由是"整个项目的表格都希望能遵守这个效果"）
- 背景：D-031 的 `page-fill` 约定要求卡片内有一个直接子元素 `.card-scroll` 承担滚动。字段页由 `InlineEditableTable` 提供，但 `SmartTable` 不提供——因此在日志页等列表页只加 `page-fill`，会出现"卡片被压缩、内容溢出卡片且无法滚动"的现象：`.page-fill > .table-card > *` 把子元素冻结在内容高度，同时没有任何元素带 `overflow: auto`。
- 决策：`SmartTable` 固定渲染 `<div className='card-scroll' ref>` 包住 `<Table>`，并默认给 Table 传 `sticky={{ getContainer: () => scrollRef.current ?? window }}`。
  - 搜索区 / 工具栏仍留在 `.card-scroll` 外层，因此在 `page-fill` 页面里保持固定不动，只有表格区域滚动。
  - `sticky` 写在 `{...tableProps}` 之前，页面若显式传 `sticky` 仍以页面为准。
- 为什么这次放进 SmartTable（与 D-028 拒绝放入列渲染的区别）：SmartTable 本来就拥有这一块的布局职责（搜索区、工具栏行、分页都由它渲染），滚动容器属于同一职责；而"某个单元格怎么渲染"不属于。判断标准是职责归属，不是"是否通用"。
- 影响面：
  - **所有**使用 SmartTable 的页面都会获得 antd 的固定表头（antd 会把表头拆成独立的 `.ant-table-sticky-holder`），并可能出现用于横向滚动的吸附式滚动条（`.ant-table-sticky-scroll`，仅在需要横向滚动时显示）。
  - 未加 `page-fill` 的页面**不会**启用"卡片内滚动"——`.card-scroll` 的样式选择器限定在 `.page-fill > .table-card > .card-scroll` 之下，此时它等同于一个普通 div。
- 已知取舍（需人工确认）：分页控件位于 `.card-scroll` 内部，因此在启用 `page-fill` 且行数超出卡片高度时，**分页会随内容滚动**；日志页每页 10 行通常不会触发。若要固定分页，需改走 antd `scroll.y` 或调整内部结构，另行评估。
- 验证：`tsc --noEmit` 通过、`npm run build` 通过；布局与表头效果必须浏览器目视确认（见 `HANDOFF.md` §4）。
- 本次启用页面：`pages/system/operatelog`（用户自行添加）、`pages/system/loginlog` 的根节点已加 `page-fill`。其它列表页待用户逐个确认后再启用。

#### D-038 补充（2026-10-11，同轮）：滚动下沉到表体，表头与分页改为布局固定

用户实测后提出两点：分页会跟着滚；以及在"看起来没超过卡片高度"的页面（`loginlog`）会出现一条只能滚一点点、形似"死"的滚动条。经核对，后者是**真实溢出**而非伪滚动条：

- 在 `page-fill` 下 `卡片高度 = min(内容高度, 可用高度)`，所以"内容没超过卡片"在溢出时恒成立，不能作为判据；真正的判据是**内容 vs 可用高度**。
- `loginlog` 按 10 行、默认表密度估算，纵向需求约 956px（顶栏 66 + 内容区 padding 36 + page-head 82 + 卡片 padding 48 + 工具栏 56 + 表头 55 + 10 行约 550 + 表体横向滚动条 15 + 分页 48）；而 1080p 屏幕的浏览器内视口通常只有 880~950px，因此**必然小幅溢出**（实测约十几像素，正好表现为"能滚动一点点"）。

修正后的机制（`global.css` 的 `.card-scroll` 一组规则）：

- `.card-scroll` 只做 flex 传高度并**不再自己滚动**（保留 `overflow: auto` 作为兜底：宁可出现滚动条，也不要因结构变化静默裁掉数据）。
- 高度沿 antd 的 DOM 链传导：`.ant-table-wrapper` → `.ant-table` → `.ant-table-container` → **只有 `.ant-table-body` 滚动**。
- 表头 `.ant-table-sticky-holder` 与分页 `.ant-pagination` 都成为滚动区之外的兄弟节点，**由 flex 布局钉住**（比 `position: sticky` 更可靠）；表头依旧依赖 `sticky` 属性把表头与表体拆开。
- `.ant-table-body` 需要 `overflow-y: auto !important`：rc-table 在 `sticky` 模式下给它内联了 `overflow-y: hidden`，内联样式只能用 `!important` 覆盖。**升级 antd 大版本时必须复查这一条。**

同轮一并采纳的措施（B2）：给日志页表格加 `size='small'`，10 行高度由约 550px 降到约 390px，使 `loginlog` / `operatelog` 在常见视口下不再出现那条小行程滚动条。该项只改页面 props，不动基线组件。

- 影响面：本次改的是 `.card-scroll` 的**共同规则**，因此同时作用于字段设计页（`InlineEditableTable`）——机制由"整块滚动 + sticky 表头"变为"表体滚动 + 布局钉表头"。字段页没有分页，预期视觉一致，但**必须重新目视确认**。
- 验证：`tsc --noEmit` 通过、`npm run build` 通过（✓ built in 21.10s）；布局效果必须浏览器目视确认（见 `HANDOFF.md` §4）。

#### D-038 撤回记录（2026-10-11，日志页实验终止）

- 用户实测后决定**只在登录日志页放弃 `page-fill`**（不是放弃整个方案）。已执行的回退：
  1. 移除 `pages/system/loginlog` 根节点的 `page-fill`——该页出现过"只能滚一点点"的竖滚动条；
  2. 回退 `loginlog` 与 `operatelog` 两页 SmartTable 上的 `size='small'`（B2 无效）。
- **明确保留（用户确认"其余内容不用变"）**：
  - `pages/system/operatelog`（操作日志，即用户口中的"审计页"）的 `page-fill`：用户明确仍需要该效果，并要求保留"分页不参与滚动"的 A 设计；
  - 字段设计页（`dataasset/fields`、`transaction/fields`）的 `page-fill` 与已验证效果；
  - 上文的机制修正（A）：滚动下沉到表体、表头与分页由布局固定；
  - D-038 的 SmartTable 改动（渲染 `.card-scroll` + 默认 `sticky`），供仍使用 `page-fill` 的页面复用。
- B2 未能解决问题的原因（值得记下，避免以后重复尝试）：它只降低**行高**（10 行约 550→390px），并不改变"固定可见高度 vs 内容高度"的对抗关系；只要视口再矮一点、或页面还存在其它固定开销，就仍会溢出。它能把阈值往下挪，但不是结构性解法。
- 关键结论：在"页面高度固定为视口高度"的前提下，**只要内容超过可用高度就必然出现滚动条**，这不是缺陷而是该方案固有的代价。判断是否溢出不能用"内容有没有超过卡片高度"——`page-fill` 下卡片高度 = min(内容高度, 可用高度)，两者在溢出时恒等；真正的判据是**内容 vs 可用高度**。
- **选择器修正（2026-10-11 同日，用户实测反馈"分页仍在跟着滚"）**：A 的第一版用**直接子选择器**写高度链与分页（`.card-scroll > .ant-table-wrapper > .ant-pagination`），实测无效。原因是 antd 的 Table 渲染结构为
  `.ant-table-wrapper > .ant-spin-nested-loading > .ant-spin-container > [.ant-table, .ant-pagination]`
  ——**分页并不是 `.ant-table-wrapper` 的直接子元素**（antd 用 `<Spin>` 把表格和分页一起包住），高度链也必须在 `Spin` 的两层上继续传下去；链一断，所有元素都退回内容高度，于是 `.card-scroll` 又成了唯一的滚动者，分页跟着滚。
  修正：`.ant-table-wrapper`、`.ant-spin-nested-loading`、`.ant-spin-container`、`.ant-table`、`.ant-table-container` 统一 `display: flex; flex-direction: column; flex: 1 1 auto; min-height: 0`；分页改用**后代**选择器并 `flex: 0 0 auto`。
  教训：**给 antd 内部结构写样式时不要假设直接子关系**，先读 `node_modules/antd/es/table/InternalTable.js` 的渲染结构。升级 antd 后要复查这一组选择器。
- **两条滚动条的成因与修正（同日，用户实测反馈）**：上一版为了"兜底"在 `.card-scroll` 上加了 `overflow: auto`，而此时 `.ant-table-body` 也是滚动容器，于是**同时出现两条滚动条**。已移除该声明——`.card-scroll` 保持 `overflow: visible`，滚动只由 `.ant-table-body` 承担。链若断掉，表现是内容溢出卡片（肉眼可见、不丢数据），不会静默裁掉数据，也不会多出第二条滚动条。
- **最终形态**（`global.css`）：`.card-scroll` 只做 flex 传高度且**不设 overflow** → 穿过 `.ant-table-wrapper` / `.ant-spin-nested-loading` / `.ant-spin-container` / `.ant-table` / `.ant-table-container` 的 flex 列链 → `.ant-table-body` 是唯一滚动者（`overflow-y: auto !important`，用于覆盖 rc-table 的内联 `overflow-y: hidden`）；表头 `.ant-table-sticky-holder`、吸附横向条 `.ant-table-sticky-scroll`、分页 `.ant-pagination` 均为 `flex: 0 0 auto`，由布局钉住。
- 复盘：这一组规则**两次**都因为偏离设计而返工——第一次把分页写成直接子选择器（antd 的 `Spin` 包装使其永不匹配），第二次自行加了 `overflow: auto`（产生第二条滚动条）。后续改动这套规则时请**先读源码确认 DOM**，并逐条对照本节。
